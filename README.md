# Ansible Patchfile Generator

This repository replaces the legacy Bash workflow composed of:

- `generate_product_patchfiles.sh`
- `generate_product_hosts.sh`
- `generate_product_varfiles.sh`
- `generate_varfile.sh`

It is designed to run from an Ansible Automation Platform (AAP) / Tower Job Template.

## What it does

The role receives two runtime inputs:

```yaml
product: java
change: CHG1400222
```

It then:

1. Clones the Elastic Inventory repository in read-only usage.
2. Reads the required `.ini` inventory files.
3. Extracts hosts and their `region`, `env`, and `location` attributes.
4. Groups hosts by product, region, environment, and location.
5. Generates the intermediate host files.
6. Generates the final Ansible YAML varfiles.
7. Clones the output repository.
8. Commits the generated files using the CHG number.
9. Pushes the commit to the configured output branch.

The Elastic Inventory repository is never modified by this role.

## Supported products

```text
java
apache
apache_sso
tomcat
jbossews
jbosseap
weblogic
```

## Inventory repository

`patch_inventory_repo_url` is the Git repository containing the source `.ini` inventories.

Expected structure:

```text
elastic_inventory/
└── inventories/
    ├── apache.ini
    ├── apache_sso.ini
    ├── tomcat.ini
    ├── jbossews.ini
    ├── jbosseap.ini
    └── weblogic.ini
```

The directory containing these files is configurable with:

```yaml
patch_inventory_subdir: inventories
```

For a normal product, the role reads the matching inventory file. For example:

```text
product=tomcat  -> inventories/tomcat.ini
product=jbosseap -> inventories/jbosseap.ini
```

For:

```text
product=java
```

the role reads all Java middleware inventories:

```text
tomcat.ini
jbossews.ini
jbosseap.ini
weblogic.ini
```

## Output repository

`patch_output_repo_url` is a separate Git repository used to persist the files generated by the Tower/AAP job.

The role writes output under:

```text
patching/
vars/
```

Example:

```text
patching/
├── java_tomcat-amer-dev-core
├── java_jbosseap-emea-prd-core
└── java_weblogic-apac-stg-dmzi

vars/
├── java_tomcat-amer-dev-core_CORE_java_AMER_CHG1400222.yml
├── java_jbosseap-emea-prd-core_CORE_java_EMEA_CHG1400222.yml
└── ...
```

The output paths can be changed with:

```yaml
patch_hostfiles_subdir: patching
patch_varfiles_subdir: vars
```

## Generated YAML

A generated varfile has the same functional data as the legacy `generate_varfile.sh` output:

```yaml
custom_hosts_list:
  - server01
  - server02

generate_excel: 'False'
location: CORE
patch_envs:
  - DEV
patch_product: java
patch_wave: 'CHG1400222'
previous_patch_wave: ''
region: AMER
```

`MZR` locations are converted to `CORE`, preserving the behavior of the legacy scripts.

For `apache_sso`, `patch_product` is written as `apache`, replacing the old post-generation `sed` operation.

# AAP / Tower configuration

## Project

Create or use an AAP/Tower Project pointing to this repository.

The Job Template must use:

```text
Playbook: playbooks/generate_patchfiles.yml
```

## Inventory

The playbook runs on `localhost`:

```yaml
hosts: localhost
gather_facts: false
```

The Tower/AAP inventory therefore needs a localhost host configured for local execution, for example:

```yaml
ansible_connection: local
```

## Job Template Extra Variables

Configure the repository information as fixed Extra Variables on the Job Template.

Example:

```yaml
patch_inventory_repo_url: "git@bitbucket.example.com:team/elastic_inventory.git"
patch_inventory_repo_version: develop

patch_output_repo_url: "git@bitbucket.example.com:team/generated_patchfiles.git"
patch_output_repo_version: develop

patch_inventory_subdir: inventories
patch_hostfiles_subdir: patching
patch_varfiles_subdir: vars

patch_git_user_name: "AAP Patchfile Generator"
patch_git_user_email: "aap-patchfiles@example.com"

patch_git_push: true
```

### Required repository variables

| Variable | Purpose |
| --- | --- |
| `patch_inventory_repo_url` | Source Git repository containing the `.ini` inventories. |
| `patch_inventory_repo_version` | Branch/tag/commit to read from the inventory repository. |
| `patch_output_repo_url` | Git repository where generated files are committed and pushed. |
| `patch_output_repo_version` | Output repository branch. |

The remaining variables have defaults and only need to be overridden when the repository layout differs.

## Job Template Survey

The operator should only provide `product` and `change` when launching the job.

### Survey field 1: Product

```text
Question: Product
Answer variable name: product
Answer type: Multiple Choice
Required: Yes
```

Choices:

```text
java
apache
apache_sso
tomcat
jbossews
jbosseap
weblogic
```

### Survey field 2: Change

```text
Question: Change
Answer variable name: change
Answer type: Text
Required: Yes
```

Example value:

```text
CHG1400222
```

The role validates the change number using:

```text
^CHG[0-9]+$
```

## Credentials

Credentials must not be stored in this repository or passed through Survey variables.

The AAP/Tower Job Template needs Git authentication that provides:

```text
Elastic Inventory repository -> READ access
Output repository            -> READ + WRITE access
```

The exact credential configuration depends on whether the internal Git service uses SSH keys, HTTPS tokens, or another authentication mechanism supported by the execution environment.

## Execution example

An operator launches the Job Template with:

```yaml
product: java
change: CHG1400222
```

Conceptually the execution is:

```text
elastic_inventory.git
        |
        | read .ini files
        v
AAP/Tower Job
        |
        | generate host groups and YAML varfiles
        v
generated_patchfiles.git
        |
        +-- git add
        +-- git commit -m "CHG1400222 - generated java patch files"
        +-- git push
```

The generated files therefore survive the Tower/AAP execution because they are persisted in the output Git repository rather than in the ephemeral execution environment.

## Legacy Bash differences

The role intentionally does not reproduce inconsistencies found in the original Bash implementation.

In particular, the legacy `generate_product_varfiles.sh` called `generate_varfile.sh` without all the values later required by `generate_varfile.sh`, including `region`, `patch_envs`, and `patch_wave`.

The Ansible role derives these values directly from the inventory data and generates the final YAML without chaining the legacy shell scripts.
